# API сервисов ИТМО

Описание программных интерфейсов студенческих сервисов Университета ИТМО: my.itmo.ru, БАРС, ИСУ, ITMO.ID и бэкендов
мобильного приложения my.itmo. Оно не привязано к языку: по этим документам и спецификациям OpenAPI можно написать
свой клиент на Python, Go, TypeScript или чём угодно ещё.

> Неофициальное описание. API принадлежат Университету ИТМО и могут измениться без предупреждения. Всё здесь
> восстановлено по веб-клиентам, мобильному приложению и живым ответам. В документах нет персональных данных,
> токенов и cookie: примеры ответов обезличены.

Готовые реализации по этому описанию:

- [my-itmo-api](../README.md) - библиотека Kotlin Multiplatform из этого репозитория (Kotlin, Java, Android, iOS);
- [itmo-mcp](https://github.com/alllexey-dev/itmo-mcp) - MCP-сервер на TypeScript с клиентом, сгенерированным из
  [openapi/my-itmo.yaml](openapi/my-itmo.yaml) и [openapi/bars.yaml](openapi/bars.yaml).

## Свой клиент за четыре шага

### 1. Получите токен

my.itmo.ru принимает access token ITMO.ID (Keycloak) публичного клиента `student-personal-cabinet`; дальше в
документах он называется токеном my.itmo.ru. Способов получить его три, и выбор зависит от того, что вы пишете:

| Что вы пишете | Способ | Что учесть |
|---|---|---|
| Скрипт, бот или сервер для своего аккаунта | [Вход по логину и паролю](auth.md#поток-2-вход-по-логину-и-паролю-без-браузера): ваш код сам отправляет форму входа | Самый короткий путь, так входят my-itmo-api и itmo-mcp. Дополнительные шаги входа (второй фактор) не проходит. Проверено на живом аккаунте |
| Приложение, которым пользуются другие люди | [Вход в браузере](auth.md#поток-1-вход-в-браузере-authorization-code-и-pkce): пользователь вводит пароль на странице ITMO.ID, вы перехватываете callback | Пароль не проходит через ваш код. Нужен WebView или другой способ увидеть редирект |
| У вас уже есть cookie `KEYCLOAK_IDENTITY` | [Тихий вход](auth.md#поток-3-тихий-вход-по-cookie-keycloak_identity): один запрос без пароля | Тем же способом получают и продлевают сессию БАРС |

Итог любого из них - пара токенов: `access_token` на 30 минут и `refresh_token` на 30 дней.

Дальше токен обновляется одним запросом:

```bash
curl -s https://id.itmo.ru/auth/realms/itmo/protocol/openid-connect/token \
  -d grant_type=refresh_token \
  -d client_id=student-personal-cabinet \
  -d "refresh_token=<refresh_token>"
```

Refresh token при каждом обновлении меняется: новый нужно сразу сохранить, старый больше не работает.

### 2. Вызовите ручку

```bash
curl -s "https://my.itmo.ru/api/schedule/schedule/personal?date_start=2026-10-05&date_end=2026-10-11" \
  -H "Authorization: Bearer <access_token>" \
  -H "Accept-Language: ru"
```

Ответ - по элементу на каждый день диапазона. Пример синтетический и сокращён до одного дня и одной пары:

```json
{
  "code": 0,
  "message": null,
  "data": [
    {
      "date": "2026-10-05",
      "day_number": 1,
      "week_number": 6,
      "lessons": [
        {
          "pair_id": 9000001,
          "subject": "Тестовая дисциплина",
          "type": "Лекция",
          "time_start": "08:20",
          "time_end": "09:50",
          "teacher_id": 200001,
          "teacher_name": "Преподаватель Тестовый",
          "room": "1404",
          "building": "Кронверкский пр., д.49, лит.А",
          "work_type_id": 1,
          "flow_type_id": 2,
          "format_id": 1
        }
      ]
    }
  ]
}
```

Полные образцы ответов основных ручек лежат в тестовых фикстурах библиотеки: [../fixtures/](../fixtures/), например
[../fixtures/schedule/personal.json](../fixtures/schedule/personal.json),
[../fixtures/recordbook/](../fixtures/recordbook/) и [../fixtures/bars/](../fixtures/bars/). Они синтетические:
написаны вручную по наблюдаемой форме ответов, настоящих данных в них нет. Файлы с `error` в имени - исключение:
это выдуманные ошибки для тестов библиотеки, а не снятые ответы.

Все пути my.itmo.ru начинаются с `https://my.itmo.ru/api/`. БАРС живёт на другом хосте и со своей сессией, не с этим
токеном: см. [auth.md](auth.md#сессия-барс).

### 3. Разберите конверт и ошибки

HTTP 200 ещё не значит успех. Почти все ответы my.itmo.ru обёрнуты в конверт, и смотреть нужно на код внутри него:

```json
{"error_code": 0, "error_message": null, "result": "<данные>"}
```

Расписание - исключение, у него свой конверт, как в примере выше:

```json
{"code": 0, "message": null, "data": "<данные>"}
```

| Что пришло | Что это значит |
|---|---|
| Код в конверте 0 (у части сервисов `null`) | Успех, данные в `result` или `data` |
| Код в конверте не 0, HTTP 200, 400, 403 или 404 | Ошибка API; полагаться можно на код, не на текст сообщения. Проверяйте и `error_code`, и `code`, какой бы конверт вы ни ждали. Редкие исключения - в [conventions.md](conventions.md) |
| HTTP 401 | Токен не принят (в конверте код 93, у спорта 92): обновите его и повторите запрос один раз |
| HTTP 403 | Токен в порядке, но доступа к ресурсу нет: например, закрыта выборность (код 112). С кодом 90 - в запросе нет заголовка `Authorization` |
| Ответ не JSON (например, `404 page not found`) | Такого пути нет или бэкенд за прокси недоступен |

Сервер добавляет поля без предупреждения: разбирайте ответы, не падая на неизвестных полях. Все конверты, известные
коды ошибок, форматы дат и причуды собраны в [conventions.md](conventions.md).

## Статусы

Каждая ручка в документах помечена тем, насколько её описанию можно доверять:

| Статус | Значение |
|---|---|
| **проверено** | Вызвана на живом аккаунте: ответ сверен со схемой или действие выполнено и откатано. У статуса две силы, см. ниже |
| **сайт** | Найдена в коде веб-клиента my.itmo.ru или БАРС; тело и параметры восстановлены по коду, но не вызывались |
| **приложение** | Найдена в Android-приложении my.itmo (URL-константа и вызов в коде); не вызывалась |
| **проекты** | Описана или реализована в проектах автора: my-itmo-api, ITMO.Widgets, itmo-fastpick, itmo-widgets-backend |

Если источников несколько, указывается самый сильный. Как проводилась живая проверка: [sources.md](sources.md).

"Проверено" бывает двух сил:

- **Перепроверяемое.** Операции [openapi/my-itmo.yaml](openapi/my-itmo.yaml) и [openapi/bars.yaml](openapi/bars.yaml).
  Каждую их GET-операцию вызывает живая проверка itmo-mcp (`npm run verify:live`) и сверяет ответ со схемой; прогон
  можно повторить в любой момент. Последний записанный прогон - 2026-10-05, все операции прошли.
- **Снятое один раз.** Всё остальное со статусом "проверено", включая три исследовательские спецификации: один живой
  ответ одного студенческого аккаунта (2026-10-05), схема выведена из него. Если ответ был пустым или не дал формы
  данных, в скобках после статуса сказано, что именно наблюдалось, например "проверено (пустой ответ)".

## Генерация клиента

Спецификации написаны в OpenAPI 3.1: убедитесь, что ваш генератор его понимает.

Типы для TypeScript (так сгенерирован клиент itmo-mcp):

```bash
npx openapi-typescript spec/openapi/my-itmo.yaml -o my-itmo.ts
```

Клиент на другом языке через OpenAPI Generator, например на Python:

```bash
npx @openapitools/openapi-generator-cli generate -i spec/openapi/my-itmo.yaml -g python -o my-itmo-client
```

`openapi-typescript` проверен на всех пяти файлах; с OpenAPI Generator эти спецификации не проверялись. Что генератор не сделает за вас:

- вход и обновление токенов: это отдельный код по [auth.md](auth.md);
- проверку кода в конверте при HTTP 200;
- причуды отдельных полей из [conventions.md](conventions.md), например `unavailable_reasons` у спорта.

Сессия БАРС в `bars.yaml` описана как схема `http`/`bearer`, а заголовок `authorization` из ответа `/login` уже
содержит `Bearer `. Сгенерированный клиент допишет префикс сам, поэтому ему передавайте значение без `Bearer `,
иначе уйдёт `Bearer Bearer ...`. Клиент, написанный вручную, отправляет значение заголовка обратно как есть.

Исследовательские спецификации ссылаются на основные по имени файла (`my-itmo-extra.yaml` и `itmo-services.yaml` - на
`my-itmo.yaml`, `bars-extra.yaml` - на `bars.yaml`), поэтому держите все файлы в одной папке.

## Проверка спецификаций

```bash
cd spec/tools
npm ci
npm run lint      # redocly lint всех пяти спецификаций
npm run examples  # примеры из openapi/examples против схем
```

То же самое выполняет CI при изменениях в `spec/`.

## Шаблон документа сервиса

1. Назначение: что это и кому доступно (студенты, сотрудники).
2. Хосты и авторизация.
3. Ручки: таблица `Метод | Путь | Что делает | Статус`.
4. Модели и правила: важные поля, коды, ограничения, побочные эффекты.
5. Спецификация: в каких файлах OpenAPI описан сервис.
6. Реализации: какие методы my-itmo-api и инструменты itmo-mcp работают с сервисом.
7. Риски и открытые вопросы.

## Как дополнить

- Новая ручка сначала попадает в таблицу документа сервиса с честным статусом.
- В спецификацию она попадает после того, как ответ снят вживую и обезличен: имена, номера ИСУ, идентификаторы,
  телефоны и тексты заменены синтетическими значениями (в itmo-mcp для этого есть
  [scripts/sanitize-fixture.ts](https://github.com/alllexey-dev/itmo-mcp/blob/main/scripts/sanitize-fixture.ts)).
  Обезличенный ответ кладётся в `openapi/examples/<operationId>.json` и должен проходить `npm run examples`.
- Токены, cookie, сырые ответы и HAR-записи в репозиторий не попадают.

Что не входит в репозиторий, перечислено в [sources.md](sources.md).
